# ElevenLabs Voice-to-Voice Agent — Complete Guide

## What This Project Does

This is a **voice-to-voice AI agent** built using the Model Context Protocol (MCP). You speak into your microphone, the AI transcribes your voice, thinks, and ElevenLabs speaks the response back through your speakers. It is also usable as a standard text chatbot.

The project demonstrates all three MCP primitives: **Tools**, **Prompts**, and **Resources** — making it a full-featured, prompt-centric MCP implementation.

## File-by-File Breakdown

### 1. `src/elevenlabs-client.ts` — API Wrapper

A clean HTTP wrapper around the ElevenLabs REST API. No MCP logic here — just one class, one responsibility.

**Methods:**

| Method | Endpoint | What it returns |
|---|---|---|
| `listVoices()` | `GET /v1/voices` | All available voices |
| `getVoice(id)` | `GET /v1/voices/{id}` | Single voice details |
| `listModels()` | `GET /v1/models` | All TTS/STT models |
| `textToSpeech(voiceId, text, model, settings?)` | `POST /v1/text-to-speech/{id}` | Raw MP3 audio as a `Buffer` |
| `speechToText(buffer, filename, model?)` | `POST /v1/speech-to-text` | Transcript string |
| `getUserInfo()` | `GET /v1/user` | Account and usage info |
| `getHistory(pageSize?)` | `GET /v1/history` | Past generation records |

`speechToText` uses `FormData` + `Blob` to send the audio as `multipart/form-data`. The API key goes in the `xi-api-key` header (do not set `Content-Type` — Node.js `fetch` sets the multipart boundary automatically).

### 2. `src/index.ts` — MCP Server

The MCP server exposes **7 tools**, **4 prompts**, and **2 resources** registered using the `@modelcontextprotocol/sdk` v1.29 non-deprecated API (`registerTool`, `registerPrompt`, `resource`).

#### Tools

Each tool maps directly to a method in `ElevenLabsClient`:

| Tool | Key behaviour |
|---|---|
| `list_voices` | Returns a compact summary (ID, name, category, labels) |
| `get_voice` | Returns full details for one voice |
| `list_models` | Returns model capabilities and supported language list |
| `text_to_speech` | Saves MP3 to `ELEVENLABS_OUTPUT_DIR` (or cwd), returns the file path |
| `speech_to_text` | Reads an audio file from disk, sends to ElevenLabs STT, returns transcript |
| `get_user_info` | Returns JSON with character quota and usage |
| `get_history` | Returns paginated generation history |

`text_to_speech` outputs: `"Audio saved to: /path/file.mp3 (N bytes, voice: ..., model: ...)"` — the client parses this string to auto-play the file.

#### Prompts

Prompts are registered with `server.registerPrompt(name, { description, argsSchema }, callback)`. Each callback returns `{ messages: [{ role, content }] }`.

**Why prompts vs. tools:** Tools are imperative (do X). Prompts are declarative — they set up a full conversation context that shapes *how* the LLM behaves for an entire session.

| Prompt | What the callback does |
|---|---|
| `voice_agent_persona` | Fetches live voice list, injects it into a system-level user message defining the agent's name, personality, and voice selection rules |
| `start_voice_session` | Builds a message that sets strict voice-mode rules: always call TTS, keep responses brief, spoken language only |
| `find_voice_for_role` | Returns a structured instruction for the LLM to call `list_voices`, reason about labels, pick top 3, and generate samples |
| `voice_showcase` | Returns an instruction to render a phrase across N diverse voices |

## The 4 Prompts — What They Do and How to Use Them

### Prompt 1: `voice_agent_persona`

**When to use:** You want a named AI character with a consistent personality and voice that greets you and responds in character on every turn.

**What happens internally:** When invoked, the prompt callback calls `client.listVoices()` live against the ElevenLabs API and bakes the full, current voice list into the LLM's instructions. The LLM then picks the best matching voice and uses it for all subsequent replies.

**How to invoke:**
```
/prompt voice_agent_persona name="Aria" personality="warm and professional" voice_style="calm and clear"
```

**Other examples:**
```
/prompt voice_agent_persona name="Max" personality="witty and casual"
/prompt voice_agent_persona name="Nova" personality="energetic and enthusiastic" voice_style="bright and upbeat"
/prompt voice_agent_persona name="Sage" personality="calm and wise" voice_style="deep and measured"
```

**What you will see in the terminal:**
```
Loading prompt "voice_agent_persona"...

  [tool: list_voices]       ← fires BEFORE the LLM is called (inside the prompt callback)
  [tool: text_to_speech]    ← LLM picked a voice and spoke its greeting
```
#### Resources

Resources expose live data the LLM can read as context, without making a tool call.

| URI | What it fetches |
|---|---|
| `elevenlabs://voices` | `client.listVoices()` → JSON |
| `elevenlabs://models` | `client.listModels()` → JSON |

Registered with `server.resource(name, uri, { description, mimeType }, readCallback)`.

### 3. `src/client.ts` — CLI Client

The standalone client that ties everything together. It spawns the MCP server as a child process and communicates over stdio. Supports both text and voice modes, and both Anthropic and OpenAI providers.

#### Key sections

**`createMcpClient()`** — spawns `build/index.js` via `StdioClientTransport`. The `ELEVENLABS_API_KEY` is forwarded from the parent environment to the child process.

**`chatAnthropic()` / `chatOpenAI()`** — agentic tool-use loops. Both functions:
1. Add the user message to history
2. Call the LLM with all available tools
3. If the LLM returns `tool_use` / `tool_calls`, dispatch each to the MCP server
4. Send tool results back to the LLM
5. Repeat until the LLM returns a final text response

`chatAnthropic` accepts an optional `systemOverride` parameter — used in voice mode to replace the default system message with `VOICE_SYSTEM`, which instructs the LLM to always call `text_to_speech`.

**`listPromptsCmd()`** — calls `mcpClient.listPrompts()` and prints name, description, and argument list.

**`invokePromptCmd()`** — calls `mcpClient.getPrompt({ name, arguments })`, injects the returned messages into conversation history, then calls the LLM to generate the first response.

**`voiceLoop()`** — the voice-to-voice loop:
1. Check sox is installed (`which rec`)
2. Spawn `rec` to record microphone → temp WAV file
3. User presses Enter to stop recording
4. Call `speech_to_text` tool with the file path → transcript
5. Call the LLM (with `VOICE_SYSTEM` override) → response
6. Parse the response for an MP3 path from `text_to_speech`
7. Play the MP3 via `afplay` (macOS) or `mpg123` (Linux)
8. If the LLM didn't call TTS itself, call it as a fallback
9. Loop

**`extractMp3Path()`** — parses the `"Audio saved to: /path/file.mp3"` string that `text_to_speech` returns. Used by both text and voice modes to auto-play generated audio.

#### REPL commands

| Input | Action |
|---|---|
| (any text) | Regular chat with LLM + tool use |
| `/prompts` | List available MCP prompts |
| `/prompt <name> [key="value"]` | Invoke a prompt and start a conversation |
| `/voice` | Enter voice conversation mode |
| `exit` / `quit` | Exit |

## How It All Connects

```
You (mic/keyboard)
    │
    ▼
client.ts ──────────────────────────────► LLM API (Claude / GPT)
│  (MCP stdio transport)                         │
│  spawns as child process                        │ tool_use / tool_calls
▼                                                ▼
index.ts (MCP Server)  ◄─────────────── client.ts dispatches tool calls
    │                                   and sends results back to LLM
    ▼
elevenlabs-client.ts ──► ElevenLabs REST API
```

**Voice loop detail:**
```
mic → sox rec → WAV file
                  ↓
          speech_to_text tool → transcript
                  ↓
             LLM (VOICE_SYSTEM) → response text + text_to_speech call
                  ↓
          text_to_speech tool → MP3 file
                  ↓
           afplay / mpg123 → audio output
```

## Steps to Run

### 1. Install Node.js ≥ 18 and sox

```bash
node --version     # need v18+
brew install sox   # macOS — needed for /voice mode
```

### 2. Get API keys

- **ElevenLabs:** https://elevenlabs.io → Profile → API Keys → Create Key
  Enable: Text to Speech (Access), Speech to Text (Access), Voices (Read), Models (Access), History (Read), User (Read)
- **Anthropic:** https://console.anthropic.com → API Keys
- **OpenAI (alternative):** https://platform.openai.com/api-keys

### 3. Set environment variables

```bash
export ELEVENLABS_API_KEY="your-elevenlabs-key"
export LLM_PROVIDER="anthropic"          # or "openai"
export ANTHROPIC_API_KEY="your-anthropic-key"
# export OPENAI_API_KEY="your-openai-key"
# export ELEVENLABS_OUTPUT_DIR="./output"
```

The server reads from `process.env` directly — `.env` is not auto-loaded. These must be exported in your shell.

### 4. Install and build

```bash
npm install
npm run build
```

### 5. Run

```bash
npm run client
```

### 6. Example session

```
You: /prompts                        ← see all 4 prompts

You: /prompt voice_agent_persona name="Aria" personality="warm and professional"
# → LLM picks best voice, generates intro audio, plays it

You: /voice                          ← enter voice loop
Press ENTER to speak:
  Recording... Press ENTER to stop:
  Transcribing...
You: "Tell me about the available voices"
  [tool: list_voices]
  [tool: text_to_speech]
Assistant: (audio plays)

You: /prompt voice_showcase phrase="Hello, I'm your AI assistant" count="4"
# → generates 4 MP3 files with different voices
```

## Key Concepts

**MCP Tools** — imperative actions (call an API, save a file). The AI decides when to use them based on the conversation.

**MCP Prompts** — pre-built conversation starters that inject a rich context into the AI's next turn. They can fetch live data (like the voice list) at invocation time and bake it into the instructions.

**MCP Resources** — structured data the AI can read passively as context, without an explicit tool call. Useful in MCP clients that support resource subscriptions (Claude Desktop, Claude Code).

**Stdio Transport** — the MCP server runs as a child process; the client and server communicate by piping JSON-RPC messages through stdin/stdout. No HTTP server needed.

**Why both Anthropic and OpenAI** — the MCP server is LLM-agnostic. The client translates between each provider's tool-call format and MCP's format. Same server, any AI.
